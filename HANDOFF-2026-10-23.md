## What OpenHW does now

- **Sensors Status window** in HWiNFO's layout (`reference/` captures): ~20 device groups, Current/Min/Max/Average,
  collapsible groups and per-core rows (collapsed groups aren't read; gray = stale), changed-value highlight.
  Engines per sensor suite: hwmon (libsensors), **HSMP** (FCLK, MCLK, core clock limit, active frequency limit and
  which of 8 sources sets it, C0 residency, DRAM bandwidth, PROCHOT), NVIDIA (NVML), NVMe, EDAC, system, network.
- **Every row's tooltip explains the reading** in plain language (`SensorExplanations`), after any
  unconfirmed-mapping caveat and before source/id. A live-machine test fails if a shown row has no specific
  explanation — add a rule when new sensors appear.
- **Board profile** (TRX50-SAGE): Super I/O voltages, temperatures and fans carry HWiNFO's names, matched by
  measurement (evidence in `docs/board-profiles.md`). in6 = CPU Core1 (Vcore1, feeds CCD1+CCD2) confirmed by a
  per-CCD sweep; in13 CPU VSOC, temp8 "CPU" and temp9 "CPU (Weighted Value)" are still inferred.
- **Menu bar**: File (Settings…, Hide Window Ctrl+W, Exit Ctrl+Q) · View (Expand/Collapse All, Reset Ctrl+R) ·
  Power (profiles, CPU Frequency… Ctrl+F, Power Limits… Ctrl+L, Remove Unexpected CPU Cap) · Help (About). Footer
  keeps icon shortcuts. **New features get a menu entry first.**
- **Sensor row right-click menu** = HWiNFO's, item for item: Add to tray / Remove from tray / Tray icon settings…
  work; the rest are grayed with a "To be implemented" tooltip.
- **Power modes**: switch power-profiles-daemon's profile (footer, Power menu, tray). When a profile change turns
  CPU boost back on, every core goes back to its OpenHW cap or the hardware maximum (the 4.0 GHz clamp, below).
- **CPU Frequency window**: all-core or per-core caps (both SMT threads), CCD, live clock; optional re-apply when
  OpenHW starts.
- **Power Limits window**: CPU PPT (50 W to the SMU's `power1_cap_max`) and each GPU's limit (NVML range), live and
  **at boot** — the CPU boot value in `/etc/hsmp-control/ppt_mw` (100–300 W, hsmp-control's own range), GPU boot
  values in OpenHW's drop-in `nvidia-power-limit.service.d/openhw.conf` (the unit is never edited). Shows what is
  limiting the CPU right now.
- **Settings** (File → Settings, tray): poll interval, start at login (`--tray`), single instance (second launch
  shows the window), tray icons (sensor via a searchable list — already-in-tray sensors grayed — color, order),
  **custom colors** (saved palette with hex codes; add by hex or the color dialog, which has a synced hex field).
- **Tray icons**: up to 8, value drawn on a colored tile (narrow bold digits), panel order = Settings order. Each
  icon's own menu: its sensor's reading, min/max/avg, device and explanation (live), then Move left/right, Remove
  from tray, Color submenu (presets + custom colors), then the app items. GNOME's AppIndicators extension shows **no
  tooltips at all**, so this menu is where the details live (the owner chose to leave hover for later).
- **openhw-helper v5** (root, `/run/openhw/helper.sock`, root:openhw 0660): `ping`, `nvmesmart`, `cpufreqmax`,
  `cpufreqrestore`, `gpupower`, `cpuppt`, `cpupptboot`, `gpupowerboot`. Fixed commands, ranges from the hardware,
  every write read back; sandboxed unit (writes only cpufreq, the HSMP power cap, `/etc/hsmp-control`, the drop-in
  directory; devices NVMe r + NVIDIA rw).

## The 4.0 GHz clamp (why the power-mode fix exists)

Power saver turns per-policy cpufreq `boost` off and the kernel holds every `scaling_max_freq` at base (4.0 GHz).
Switching back restores the **stored max request**. Normally that's the previous ceiling, but a request written
while boost is off is 4.0 GHz — e.g. OpenFan's *Hardware maximum* pressed in power-saver (reproduced) — and then
"performance" silently runs at base clock until reboot. A reboot in power-saver does **not** cause it (tested).
OpenHW's fix restores each core to its OpenHW cap or the hardware maximum on every boost off→on transition; other
low ceilings are only reported ("Capped at …"). The OpenFan side is written up in openfan-linux
`CPU-BOOST-CLAMP-README.md`.

## Decisions to keep

- **Standalone, and smarter than OpenFan.** Never reference openfan-linux; don't copy its logic blindly either —
  derive behaviour from the hardware's own interfaces (e.g. the PPT range from `power1_cap_max`).
- **Helper commands are fixed and validated**; ranges come from the hardware; writes are read back. Reinstall
  needs the owner's sudo (open `sudo packaging/install-helper.sh` in a terminal tab for them).
- **Boot values live in the owner's existing boot services**, never a new boot path.
- **Menu first**; footer = icon shortcuts. Unimplemented HWiNFO items are shown grayed "To be implemented".
- **Versioning**: semantic, pre-1.0 — bump the **minor** in `Directory.Build.props` for a round of new features, the
  **patch** for fixes only; add a CHANGELOG.md entry and tag `vX.Y.Z` (pushed with `--tags`). Current: **0.2.0**.
- **US spelling on screen** ("Color"). The settings JSON keeps the `Colour` field name so existing files load.
- **Headless testing first**; GUI captures (`import -window <xid>`) for visual changes; never inject desktop input —
  drive the same helper/D-Bus calls instead, and restore whatever a live test changes.

## Gotchas learned the hard way

- **The owner may be using OpenHW while tests run** (a cleared caps file was their click). Ask before calling it a bug.
- **GNOME tray**: no tooltips; each new icon is inserted left of earlier ones (register last-first);
  `LayoutUpdated` rebuilds the menu and closes open submenus — use `ItemsPropertiesUpdated` for changing labels.
- **power-profiles-daemon** announces `ActiveProfile` before it flips boost: wait for boost to match the profile.
- **amd-pstate**: `cpuinfo_max_freq` is 4.0 GHz with boost off; a "hardware maximum" written then stores 4.0 GHz.
- **hsmp-control** refuses boot values outside 100–300 W; the live SMU limit goes to `power1_cap_max`.
- **Helper replies are ASCII** (write "to", not "–").
- **Tmds.DBus.Protocol `MessageWriter` is a ref struct**: pass by ref, never `using var` when passing by ref, and
  don't hold one in an async method. Avalonia 11.2.3 pins Tmds.DBus.Protocol 0.20.0 (NU1903) — upgrade together.
- **Avalonia**: menu gestures are labels only (KeyBindings added separately); `ContextMenu.Opening` fires only via a
  context request (tests raise `ContextRequestedEvent`); disabled items need `ToolTip.ShowOnDisabled`; NumericUpDown
  contains a TextBox; headless captures don't include popups.
- **Commit before `packaging/install-app.sh`**: the footer/About version is `git describe --dirty` at build time, so
  installing with uncommitted edits shows "-dirty" until the next install.
- **OpenHW is Linux-only**, declared once per project (`Platform.cs`).
- **Lingering is enabled for `russellm`**: new group membership needs a reboot. **NTFS mount**: `core.filemode` is
  false — `git update-index --chmod=+x`.
- `/mnt/SOLIDIGM/CLAUDE.md` (website recreation, PowerShell, Windows paths) doesn't apply to this project.
