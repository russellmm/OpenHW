# OpenHW handoff — 2026-10-26

HWiNFO64-style hardware monitor for Ubuntu 26.10 / GNOME (Wayland session; the app runs under XWayland), built on
the owner's TRX50 workstation (Threadripper 9970X, ASUS Pro WS TRX50-SAGE WIFI A, 1× RTX 5060 Ti + 2× RTX PRO 6000
Blackwell, 7 NVMe drives). Repo `/mnt/SOLIDIGM/Claude/OpenHW` → github.com/russellmm/OpenHW (`main`). Avalonia
11.3.22 / .NET 8. Planned work: [ROADMAP.md](ROADMAP.md). User-facing description: [README.md](README.md). Earlier
handoffs are in git history (`HANDOFF-2026-10-25.md` / `-24.md` / `-23.md` before the renames; `7736658` = the
2026-10-23 Windows-research handoff). Since 2026-10-26 OpenHW also does what the owner's RTXinVM did (lend an RTX
6000 to a Windows VM without logging out); RTXinVM is uninstalled.

## 0.16.3 (latest)

- **Launch grouping** (`Power/AppLaunches.cs`), found in the live notification test: Chrome got two notifications.
  Chromium/Electron apps move their main process into their own scope (`app-com.google.Chrome-37026.scope`) while the
  zygotes (GPU process) stay in GNOME's launch scope (`app-gnome-google\x2dchrome-37026.scope`); Claude desktop does
  the same (`app-com.anthropic.Claude-N` + `app-gnome-com.anthropic.Claude-N`). Two scopes in one app.slice are one
  launch when one owns its number (`-N.scope` with PID N in it) and the other has the same number or holds non-first
  processes whose parent is N (the first process is skipped: its parent is the launcher, e.g. OpenHW reopening
  OpenFan). Used by CardHolderWatch (one question per launch; answer applies to all its patterns; decided if any is
  ticked/left), `LendCoordinator.Blocking` (shared with the page: covered if any scope's pattern is ticked), Lend
  (stops the main scope, then the rest; reopens only the main scope's own process) and Return (stops the reopened
  scope's whole launch, via the new `PausedApp.Parent`). CardHolderWatch skips overlapping checks. Checked against
  the live system: only the Chrome and Claude pairs group. Tests: 243 (115 + 128).

## 0.10.0

- **DDR5 DIMM sensors + Infineon XDPE19283B** (roadmap "more HWiNFO sensors"; owner chose these two and deferred
  SVI3 and ASUS EC VRM). Owner-approved rules: the only SMBus write is the DIMM PMIC's ADC select **R30**; a one-time
  read-only scan (`tools/smbus-probe/`, run by the owner with sudo) found the devices.
- What's where on this board: DIMM buses = the two DesignWare adapters with spd5118 hubs at 0x50/0x52
  (`AMDI0010:01`, `:02`); per hub n: PMIC 0x48+n (**Richtek**, R3C/R3D = 8A 8C, matches SPD bytes 198–199;
  SPD byte 200 = 0x80), TS5111 thermal sensors at 0x10+n / 0x30+n (MR0 = 0x51, temp MR49/50 like spd5118). The
  XDPE19283B is on **PIIX4 port 0 (i2c-4) at 0x20**, IC_DEVICE_ID `01 95`, PAGE already 1 = the 1.35 V loop. It
  doesn't answer `i2cdetect -r`'s receive-byte on i2c-6 style probing — PMBus reads with a command code work.
- PMIC decode (RTQ5132 datasheet DSQ5132-07, JEDEC-common map): R30 = 0x80 | sel<<3 | keep[1:0], sel SWA 0, SWB 2,
  SWC 3, VIN_BULK 5, LDO1.8 8, LDO1.0 9; R31 × 15 mV (VIN × 70 mV). R1B[6]=1 & R1A[1]=1 (as the BIOS left them)
  → R0C = total power × 125 mW; otherwise per-rail current/power in R0C/R0E/R0F. BIOS leaves R30 = 0xC8; the helper
  restores it. 15 ms settle per channel is enough (checked: no stale channel across 4 DIMMs).
- Helper **protocol 7**: `ddr5` (`Ddr5Reader`: spd5118-bound hubs only, PMIC written only if its vendor id equals the
  SPD's, 1.5 s cache) and `vr` (`BoardVrReader` with the `BoardVrs` table; IC_DEVICE_ID check before any other
  read, never writes PAGE; the app blanks values when PAGE ≠ the rail page). `openhw-helper --once <cmd>` prints one
  reply (the owner ran it with sudo: all four DIMMs and the VR matched HWiNFO). Unit: `DeviceAllow=char-i2c rw`.
- App: `DimmEngine` / `BoardVrEngine`. Each DIMM is its own group `dimm:<hub identity>` (the spd5118 hwmon row
  joins it, renamed "SPD Hub Temperature"), titled "DDR5 DIMM [#i]: Kingston KF556R28-32 (AMDI0010:01 / 0x50)"
  (maker + part from the world-readable SPD eeprom; index = hub order, not HWiNFO's SMBIOS numbers). VR group
  "ASUS Pro WS TRX50-SAGE WIFI A (Infineon XDPE19283B)" sits between Nuvoton and ASUS EC (EC order 6 → 7).
  Checked with a stand-in helper socket serving the captured replies (`OPENHW_HELPER_SOCKET` + `--dump`).
- Tests: 193 (90 library incl. `SmbusSensorTests` with a fake bus/sysfs + 103 UI).

## 0.9.0

- **Bug (owner's report)**: started at login with `--tray`, the window opened later from the tray was drawn at 1×.
  Cause: the login autostart starts OpenHW (and with it XWayland) ~1 s before `gsd-xsettings` publishes `Xft.dpi`
  (journal: openhw 17:41:47, XSettings 17:41:48). Avalonia's X11 backend sees `Xft.dpi` change, but 11.2.x raised
  its screens' `Changed` without `ScreensBase.OnChanged()`, so windows re-read the cached 1× screens. Fixed upstream
  in 11.3.6 (`_impl.Changed += OnChanged`). **Avalonia upgraded 11.2.3 → 11.3.22** (Tmds.DBus.Protocol 0.20.0 →
  0.21.3 with it). Reproduced on a private Xvfb (start `--tray` with no `Xft.dpi`, `xrdb -merge` 2× later, show):
  installed 0.8.0 → 820×1000 px, new build → 1640×2000.
- 11.3 change that bit a test: ComboBox templates now contain a TextBox (editable ComboBox) — tests that grab "the
  first TextBox" must skip template parts (`TemplatedParent is null`).
- **Settings → Window scale** (`AppSettings.WindowScale`, percent, 0 = Automatic; choices in
  `Settings/WindowScale.cs`: 100–300 by 25, 350, 400). Applied in `Program.Main` before Avalonia starts, through
  Avalonia's env vars: `AVALONIA_SCREEN_SCALE_FACTORS=openhw-fixed-scale=1` (a named config matching no monitor →
  every screen 1×, so `Xft.dpi` stops counting) × `AVALONIA_GLOBAL_SCALE_FACTOR=<percent/100>`. The indexed form of
  `AVALONIA_SCREEN_SCALE_FACTORS` is unusable (Avalonia returns 1 for index 0). Automatic clears only OpenHW's own
  variables (the sentinel value marks them), since a restart inherits them. "Automatic (now N %)" shows the running
  scale when Automatic is in effect.
- **Restart OpenHW now** (shown after a scale change): `Program.RestartRequested` + normal shutdown; after the
  lifetime ends (single-instance socket released) `Program.Restart` starts the same launcher/dll without `--tray`.

  Checked on the owner's desktop with the debug build: 8 tray icons register over Tmds 0.21.3, window at 2.74×

## The 4.0 GHz clamp (why the power-mode fix exists)

Power saver turns per-policy cpufreq `boost` off and the kernel holds every `scaling_max_freq` at base (4.0 GHz).
Switching back restores the **stored max request**. Normally that's the previous ceiling, but a request written
while boost is off is 4.0 GHz — e.g. OpenFan's *Hardware maximum* pressed in power-saver (reproduced) — and then
"performance" silently runs at base clock until reboot. A reboot in power-saver does **not** cause it (tested).
OpenHW's fix restores each core to its OpenHW cap or the hardware maximum on every boost off→on transition; other
low ceilings are only reported ("Capped at …"). The OpenFan side is written up in openfan-linux
`CPU-BOOST-CLAMP-README.md`.

## Gotchas learned the hard way

- **The owner may be using OpenHW while tests run** (a cleared caps file was their click). Ask before calling it a bug.
- **GNOME tray**: no tooltips; each new icon is inserted left of earlier ones (register last-first);
  `LayoutUpdated` rebuilds the menu and closes open submenus — use `ItemsPropertiesUpdated` for changing labels.
- **power-profiles-daemon** announces `ActiveProfile` before it flips boost: wait for boost to match the profile.
- **amd-pstate**: `cpuinfo_max_freq` is 4.0 GHz with boost off; a "hardware maximum" written then stores 4.0 GHz.
- **hsmp-control** refuses boot values outside 100–300 W; the live SMU limit goes to `power1_cap_max`.
- **Helper replies are ASCII** (write "to", not "–").
- **Tmds.DBus.Protocol `MessageWriter` is a ref struct**: pass by ref, never `using var` when passing by ref, and
  don't hold one in an async method. Avalonia pins its Tmds.DBus.Protocol (11.3.22 → 0.21.3) — upgrade together.
- **Display scale on X11 = `Xft.dpi`/96** (Avalonia's default provider), live-updated since 11.3. Test scale
  behaviour on a private `Xvfb :77` with `xrdb -merge` — note Xvfb resets (and drops its X resources) when its last
  client disconnects, e.g. across an OpenHW restart.
- **Avalonia**: menu gestures are labels only (KeyBindings added separately); `ContextMenu.Opening` fires only via a
  context request (tests raise `ContextRequestedEvent`); disabled items need `ToolTip.ShowOnDisabled`; NumericUpDown
  contains a TextBox; headless captures don't include popups.
- **Per-user install shadows the package**: `~/.local/bin` comes first on PATH and `~/.local/share/applications`
  overrides `/usr/share`, so with both installed, `openhw` and the menu entry run the per-user copy.
- **Commit before `packaging/install-app.sh`**: the footer/About version is `git describe --dirty` at build time, so
  installing with uncommitted edits shows "-dirty" until the next install.
- **OpenHW is Linux-only**, declared once per project (`Platform.cs`).
- **The launcher re-executes itself** once to set `DOTNET_GCgen0size` (`Program.Gen0Budget`): the PID stays the
  same (execve), and `dotnet openhw.dll` doesn't do it.
- **Unix socket paths max out at 108 bytes**: running the tests with `TMPDIR` set to a long path makes
  `ASecondLaunchAsksTheFirstToShow` fail (its socket lands under a temp dir). Not a product bug.
- **Memory measurements are noisy** as single snapshots (GC timing): sample RSS/private every 5 s for 90 s after a
  30 s warm-up, with a copy of the owner's config (`XDG_CONFIG_HOME`), and compare medians.
- **Lingering is enabled for `russellm`**: new group membership needs a reboot. **NTFS mount**: `core.filemode` is
  false — `git update-index --chmod=+x`.
- **GNOME on Wayland only finds new extensions at login**: after installing a .deb that adds or renames the
  extension, `GetExtensionInfo` returns `{}` until the next login (OpenHW shows NeedsLogin). `EnableExtension` fails
  for an unloaded uuid, hence the `gsettings` edit. Changing an extension's *code* also needs a login to load.
- **Disabling/enabling any extension makes ubuntu-appindicators re-create every tray icon** (new panel actors):
  anything holding a panel button must re-find it (the hover extension rescans on the panel boxes' `child-added`).
- **St labels ellipsize by default**: `line_wrap` does nothing until `clutter_text.ellipsize = NONE`.
- **Headless gnome-shell needs a short `XDG_RUNTIME_DIR`** (`/run/user/<uid>/…`): the scratchpad path overflows
  the 108-byte socket limit and mutter exits with "Failed to create socket".
- **Private D-Bus test sessions must get their own `XDG_RUNTIME_DIR`** (for `dbus-run-session` itself, not just the
  app inside). On 2026-10-25 an ad-hoc exit test ran `dbus-run-session` with the real `/run/user/1000`: its
  auto-started `xdg-document-portal` took over `/run/user/1000/doc` and left it unmounted on exit, so every Flatpak
  app (Moonlight) failed with "bwrap: Can't find source path /run/user/1000/doc/by-app/…". Fixed by
  `systemctl --user restart xdg-document-portal.service`. `tools/tray-exit-test/run.sh` already does it right.
- `/mnt/SOLIDIGM/CLAUDE.md` (website recreation, PowerShell, Windows paths) doesn't apply to this project.
