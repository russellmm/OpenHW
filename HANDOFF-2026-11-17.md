## Read first — fan control as it stands (0.32.0; additions through 0.35.0 in the release sections above)

- **One screen, like OpenFan's Home**: Power → Fan Control… (also in the tray menu). **Controls**: a card per fan — the
  BMC's 7 zones and the NVIDIA fans (NVML) — with a Curve box + curve dropdown, duty and RPM, where it runs, friendly
  name (click; tooltip = original + id), ⋮ (move; BMC fans: Edit BMC curve…, Restore original). **Curves**: flat (−/+),
  graph (one sensor or the **hottest of several** — "bulk", e.g. All DIMMs — live dot on a preview, Edit → OpenFan's
  graph editor with the green dashed BMC version), mix (max/min/average; preview of the BMC curve + ⚠ when the BMC can't
  keep it). + Flat / + Graph / + Mix (New or Duplicate). Drag cards to reorder. Window ⋮: configurations (New / Save /
  Save as / Load, Ctrl+N/S/Shift+S/L; file in use in the title, auto-saved; `~/.config/openhw/fan-profiles/`).
- **Where a curve runs**: on a **BMC fan**, a curve that reads only BMC sensors (CPU Package, T_Sensor, LAN, DIMMA1–H1,
  PCIE01–07 — the slot sensors **are the GPUs' core temperatures**, measured) is **fitted to the BMC** (sensor bitmask +
  4 free points + 100 °C, never slower than drawn) and **written once** (1 write, 2 if the sensors change; then none).
  Any other sensor → **OpenHW drives it** (flash write per change: 5 % steps, a minute's hold on slow-downs, per-day
  count, warned first). **NVIDIA fans** are always driven through NVML (nothing stored, no budget; 0 % = the card's own

## 0.10.0

- **DDR5 DIMM sensors + Infineon XDPE19283B** (roadmap "more HWiNFO sensors"; owner chose these two and deferred

- What's where on this board: DIMM buses = the two DesignWare adapters with spd5118 hubs at 0x50/0x52
  (`AMDI0010:01`, `:02`); per hub n: PMIC 0x48+n (**Richtek**, R3C/R3D = 8A 8C, matches SPD bytes 198–199;
  SPD byte 200 = 0x80), TS5111 thermal sensors at 0x10+n / 0x30+n (MR0 = 0x51, temp MR49/50 like spd5118). The
  XDPE19283B is on **PIIX4 port 0 (i2c-4) at 0x20**, IC_DEVICE_ID `01 95`, PAGE already 1 = the 1.35 V loop. It
  doesn't answer `i2cdetect -r`'s receive-byte on i2c-6 style probing — PMBus reads with a command code work.
- PMIC decode (RTQ5132 datasheet DSQ5132-07, JEDEC-common map): R30 = 0x80 | sel<<3 | keep[1:0], sel SWA 0, SWB 2,
  SWC 3, VIN_BULK 5, LDO1.8 8, LDO1.0 9; R31 × 15 mV (VIN × 70 mV). R1B[6]=1 & R1A[1]=1 (as the BIOS left them)
  → R0C = total power × 125 mW; otherwise per-rail current/power in R0C/R0E/R0F. BIOS leaves R30 = 0xC8; the helper
  restores it. 15 ms settle per channel is enough (checked: no stale channel across 4 DIMMs).
- Helper **protocol 7**: `ddr5` (`Ddr5Reader`: spd5118-bound hubs only, PMIC written only if its vendor id equals the
  SPD's, 1.5 s cache) and `vr` (`BoardVrReader` with the `BoardVrs` table; IC_DEVICE_ID check before any other
  read, never writes PAGE; the app blanks values when PAGE ≠ the rail page). `openhw-helper --once <cmd>` prints one
  reply (the owner ran it with sudo: all four DIMMs and the VR matched HWiNFO). Unit: `DeviceAllow=char-i2c rw`.
- App: `DimmEngine` / `BoardVrEngine`. Each DIMM is its own group `dimm:<hub identity>` (the spd5118 hwmon row
  joins it, renamed "SPD Hub Temperature"), titled "DDR5 DIMM [#i]: Kingston KF556R28-32 (AMDI0010:01 / 0x50)"
  (maker + part from the world-readable SPD eeprom; index = hub order, not HWiNFO's SMBIOS numbers). VR group
  "ASUS Pro WS TRX50-SAGE WIFI A (Infineon XDPE19283B)" sits between Nuvoton and ASUS EC (EC order 6 → 7).

## The 4.0 GHz clamp (why the power-mode fix exists)

Power saver turns per-policy cpufreq `boost` off and the kernel holds every `scaling_max_freq` at base (4.0 GHz).
Switching back restores the **stored max request**. Normally that's the previous ceiling, but a request written
while boost is off is 4.0 GHz — e.g. OpenFan's *Hardware maximum* pressed in power-saver (reproduced) — and then
"performance" silently runs at base clock until reboot. A reboot in power-saver does **not** cause it (tested).
OpenHW's fix restores each core to its OpenHW cap or the hardware maximum on every boost off→on transition; other
low ceilings are only reported ("Capped at …"). The OpenFan side is written up in openfan-linux
`CPU-BOOST-CLAMP-README.md`.

  commit (it refuses a dirty tree; off the tag the version gets `+git.<hash>`). Output in `dist/` (gitignored).
  Then, with the owner's go-ahead, a GitHub release for the tag (CHANGELOG entry + install line as notes, the .deb

- **US spelling on screen** ("Color"). The settings JSON keeps the `Colour` field name so existing files load.
- **Headless testing first**; GUI captures (`import -window <xid>`) for visual changes; never inject desktop input —
  drive the same helper/D-Bus calls instead, and restore whatever a live test changes. Shell-side code (the GNOME

- **GPU lending is OpenHW's job now** (owner, 2026-10-25/26; RTXinVM retired 2026-10-26). Owner's requirements:
  both RTX 6000s usable by any Linux program whenever the VM isn't using one (no prefix/launcher); the hidden list is

  lend (its choice, `LendReopen`). OpenHW still keeps launchers another tool wrote, and Restart now keeps a systemd

- **Hiding an app hides everything launched from it** (same scope): never hide the Claude desktop app or a terminal
  — their child processes (vLLM, llama.cpp, nvidia-smi) would lose the card. Owner wants Claude visible (2026-10-26).
- **Never identify a GPU by its PCI address in saved config** (owner, 2026-11-14): GPU Lending and boot power limits
  use the GPU UUID and look the slot up. Libvirt's own hostdev entries are the owner's (by slot); OpenHW only reports.
- **Fan curves (owner, 2026-11-17)**: build capability, not copies of the owner's OpenFan curves. Curves on BMC sensors
  run on the BMC (no flash writes after Apply); other sensors are allowed but warned about (flash writes). Never assume
  a firmware limit no one tested (point 4 = 70 °C was one).
- **BMC writes only through the fan driver, and only what the owner asked for**: fan curves (IPMI `30 0e`), fan
  temperature sources (Redfish PATCH) and fan alarm thresholds (IPMI 04h/26h, lower three only, 0.35.0). Nothing else that sets, clears or controls (fan *modes*, SEL clear, chassis,
  BMC resets) without the owner's go-ahead. **Fan writes go to the BMC's flash** (warm and cold resets kept them):
  keep writes few — prefer BMC-run curves; OpenHW-driven duties only under a write budget.
- **Claude never signs in to the BMC itself** (web console or Redfish with a password, even from a file it doesn't
  display); authenticated checks are run by the owner. OpenHW's helper using the stored login at runtime is fine.
  Unauthenticated Redfish GETs over the host interface work (AuthNone) — but every one lands in the 150-entry Audit Log.
- **The BMC's host interface stays open (AuthNone)** — owner's choice, 2026-11-17: don't push to lock it down;
  Hardware Check shows it as a plain note.
- **BIOS Setup never writes the firmware** (owner: write-back "later, carefully"): edits are a plan; any future writer
  goes through the helper with backup, size/version checks, one variable at a time, read-back, and the owner's OK
  (docs/bios-setup.md). The Python emulator at /mnt/SOLIDIGM/Claude/BIOS is retired (owner deletes it); its tools
  live in tools/bios-data.
- **OpenHW takes over fan control from OpenFan** (owner, 2026-11-14); the goal is OpenHW alone. Never let both write
  the same fans: BMC takeovers are refused while OpenFan's BMC journal exists, GPU fans while its helper socket exists.
- **Fan UI mirrors OpenFan's Home** (owner, 2026-11-17): one screen of fan cards + curve cards; show RPM (from the BMC /
  NVML) but **no RPM calibration**; friendly names keep the original in a tooltip; say plainly what a BMC write costs
  ("one write to put it there, then none"). New fan features get tested headlessly, installed by the owner, and pushed

  be able to write bpffs (`/sys/fs/bpf`) — never re-add `ProtectKernelTunables` (it makes bpffs read-only; see

## Gotchas learned the hard way

- **The owner may be using OpenHW while tests run** (a cleared caps file was their click). Ask before calling it a bug.
- **GNOME tray**: no tooltips; each new icon is inserted left of earlier ones (register last-first);
  `LayoutUpdated` rebuilds the menu and closes open submenus — use `ItemsPropertiesUpdated` for changing labels.
- **power-profiles-daemon** announces `ActiveProfile` before it flips boost: wait for boost to match the profile.
- **amd-pstate**: `cpuinfo_max_freq` is 4.0 GHz with boost off; a "hardware maximum" written then stores 4.0 GHz.
- **hsmp-control** refuses boot values outside 100–300 W; the live SMU limit goes to `power1_cap_max`.
- **Helper replies are ASCII** (write "to", not "–").
- **Tmds.DBus.Protocol `MessageWriter` is a ref struct**: pass by ref, never `using var` when passing by ref, and
  don't hold one in an async method. Avalonia pins its Tmds.DBus.Protocol (11.3.22 → 0.21.3) — upgrade together.
- **Display scale on X11 = `Xft.dpi`/96** (Avalonia's default provider), live-updated since 11.3. Test scale
  behaviour on a private `Xvfb :77` with `xrdb -merge` — note Xvfb resets (and drops its X resources) when its last
  client disconnects, e.g. across an OpenHW restart.
- **Avalonia**: menu gestures are labels only (KeyBindings added separately); `ContextMenu.Opening` fires only via a
  context request (tests raise `ContextRequestedEvent`); disabled items need `ToolTip.ShowOnDisabled`; NumericUpDown
  contains a TextBox; headless captures don't include popups.
- **Per-user install shadows the package**: `~/.local/bin` comes first on PATH and `~/.local/share/applications`
  overrides `/usr/share`, so with both installed, `openhw` and the menu entry run the per-user copy.
- **Commit before `packaging/install-app.sh`**: the footer/About version is `git describe --dirty` at build time, so
  installing with uncommitted edits shows "-dirty" until the next install.
- **OpenHW is Linux-only**, declared once per project (`Platform.cs`).
- **The launcher re-executes itself** once to set `DOTNET_GCgen0size` (`Program.Gen0Budget`): the PID stays the
  same (execve), and `dotnet openhw.dll` doesn't do it.
- **Unix socket paths max out at 108 bytes**: running the tests with `TMPDIR` set to a long path makes
  `ASecondLaunchAsksTheFirstToShow` fail (its socket lands under a temp dir). Not a product bug.
- **Memory measurements are noisy** as single snapshots (GC timing): sample RSS/private every 5 s for 90 s after a
  30 s warm-up, with a copy of the owner's config (`XDG_CONFIG_HOME`), and compare medians.
- **Lingering is enabled for `russellm`**: new group membership needs a reboot. **NTFS mount**: `core.filemode` is
  false — `git update-index --chmod=+x`.
- **GNOME on Wayland only finds new extensions at login**: after installing a .deb that adds or renames the
  extension, `GetExtensionInfo` returns `{}` until the next login (OpenHW shows NeedsLogin). `EnableExtension` fails
  for an unloaded uuid, hence the `gsettings` edit. Changing an extension's *code* also needs a login to load.
- **Disabling/enabling any extension makes ubuntu-appindicators re-create every tray icon** (new panel actors):
  anything holding a panel button must re-find it (the hover extension rescans on the panel boxes' `child-added`).
- **St labels ellipsize by default**: `line_wrap` does nothing until `clutter_text.ellipsize = NONE`.
- **Headless gnome-shell needs a short `XDG_RUNTIME_DIR`** (`/run/user/<uid>/…`): the scratchpad path overflows
  the 108-byte socket limit and mutter exits with "Failed to create socket".
- **Private D-Bus test sessions must get their own `XDG_RUNTIME_DIR`** (for `dbus-run-session` itself, not just the
  app inside). On 2026-10-25 an ad-hoc exit test ran `dbus-run-session` with the real `/run/user/1000`: its
  auto-started `xdg-document-portal` took over `/run/user/1000/doc` and left it unmounted on exit, so every Flatpak
  app (Moonlight) failed with "bwrap: Can't find source path /run/user/1000/doc/by-app/…". Fixed by
  `systemctl --user restart xdg-document-portal.service`. `tools/tray-exit-test/run.sh` already does it right.
- **A new motherboard means a new TPM**: anything sealed with `systemd-creds` to the old TPM fails — libvirtd's
  `LoadCredentialEncrypted` secrets key did ("TPM key integrity check failed", status 243/CREDENTIALS). Move the key
  aside and restart; its init service makes a new one.
- **PCI addresses change with the board**: GPUs 01/11/E1 → 11/C1/F1, NVMe drives too. hwmon `nvme:N` ids can point
  at another drive after a swap; only a saved snapshot (Hardware Check) can tell.
- **IPMI over KCS is slow**: the first SDR read takes ~10 s; the helper sweeps on its own thread and answers from a
  cache, and the window's first `bmc` request runs off the sampling thread.
- **BMC Redfish over the host interface reads without a login — even with bogus credentials** — because the host
  interface is in AuthNone mode (credential bootstrapping as HostInterfaceAdministrator). Only a session login (POST
  Sessions → 201/401) proves a password. The host-interface NIC is renamed every boot: never pin it.
- **The BMC's Audit Log holds 150 entries and logs every in-band Redfish request**: a 700-page crawl wrapped it
  (2026-11-17). Crawl sparingly.
- **Redfish registry files come gzip-compressed with no Content-Encoding**; AMI publishes Setup checkboxes as
  true/false values with registry choices "None"/"Disabled"; some strings carry bytes after a NUL.
- **UEFI variables in efivarfs = 4 attribute bytes + data**; a size that differs from the BIOS data means another BIOS
  version. **The running firmware stores "Auto" in ASUS typed fields whose factory default is empty** — treat as equal.
- **Avalonia `FuncDataTemplate` gets called once with a null item** — templates must handle it.
- **The WireView's serial link has no checksum**: drop frames with fan duty > 100 or non-zero padding (bytes 11, 95).
  Its RTS welcome string came back empty here — identify by vendor data EF 05/06 and build info instead. Its own
  product name already includes "Thermal Grizzly".
- **SEL timestamps are UTC**; the BMC's fan alarm thresholds are stored in 120 RPM steps (360/360/0 by default).
- **The BMC's Redfish PATCH wants `Oem.Mode` and complete PWM entries**, and refuses the whole list over the unused
  8th slot while still applying the rest (so a "failed" PATCH may have changed things — read back). Send one complete
  entry as read. Details in docs/fan-control.md.
- **This BMC firmware refuses 0 % in a fan curve (0xD9) and refuses the IPMI source command (30 93 → 0xC7).** Point 5
  of a curve is at 100 °C; point 4 is free (web console edits A–D; IPMI write with point 4 = 80 °C accepted 2026-11-17).
- **The BMC's PCIe slot sensors are the GPUs' core temperatures** (~1 °C, live), not board temperatures near the slot.
- **An empty Avalonia `MenuFlyout` filled in its `Opening` event never opens**: build the items first, then `ShowAt`.
- **Fan card titles are TextBoxes** (renamable): tests reading card text must include TextBox text (`FanControlWindow.Texts`).
- **`pkill -f <pattern>` from a Bash call kills that Bash call too** when the pattern is in its own command line (exit
  144): kill by PID.
- **The BIOS hides Chassis Fan(s) Configuration on this machine** (internal Setup byte 215 = 1): the BMC owns those
  fans; set them in the BMC web console or OpenHW's Fan Control.
- **The BMC reports fans in 120 RPM steps** and its VBAT reads ~0.2 V below the Super I/O's VBAT pin.
- `/mnt/SOLIDIGM/CLAUDE.md` (website recreation, PowerShell, Windows paths) doesn't apply to this project.
